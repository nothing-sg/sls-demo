# Public access via ngrok

## Problem Statement

A developer running the local dev stack (`make backend-run`, `make frontend-run`, plus the Docker-based Postgres/`cognito-local` setup from ADR-0008) sometimes needs to share a live, working demo of the app with someone else — a colleague, a client — who doesn't have access to the developer's machine or network, and won't install any device-pairing software to get it. This is a different problem from personal phone access (ADR-0009 covers reaching the app from the developer's *own* phone via Tailscale): here the audience is a third party, and the goal is a link that works for anyone the developer chooses to send it to, without requiring anything installed on their end.

## Solution

Running `make tunnel-up` starts two ngrok tunnels — one fronting the frontend dev server, one fronting `cognito-local` — each getting its own randomly-assigned public HTTPS URL (ngrok's free tier reassigns these every session; there is no stable hostname to memorize). The developer then runs `make frontend-run-public` and `make auth-run-public` instead of the usual `frontend-run`/`auth-run`: both automatically look up the correct tunnel's current URL from ngrok's own local API and wire it in, so the developer never manually copies a URL into an environment variable. The frontend tunnel is protected by a freshly generated Basic Auth username/password, printed to the terminal when the tunnel starts, which the developer shares with their specific recipient through a separate channel from the link itself (so having the link alone isn't enough). The recipient opens the link, enters that password once, and signs in with one of the existing seeded test accounts (`local/cognito/README.md`) to use the real app.

## User Stories

1. As a developer, I want to share a working link to my local dev stack with someone who has no special software installed, so that I can demo the app to a colleague or client without deploying anything to real infrastructure.
2. As a developer, I want the tunnel URLs to be looked up automatically rather than copied by hand, so that I don't have to notice, copy, and paste a randomly-generated URL correctly every single time I start a session (ngrok's free tier assigns a new one each run).
3. As a developer, I want a password gate in front of the shared link, so that a stranger who somehow stumbles on the URL (a scanner, a search engine, a leaked chat log) can't reach even the login screen without something I explicitly gave my recipient.
4. As a developer, I want that password to be freshly generated every session rather than a fixed value, so that the gate isn't defeated by anyone who's simply read this repo's own documentation (the way the seeded Cognito test credentials already are, deliberately, for local-only use).
5. As a developer, I want to give my recipient a link and a password through two different channels (e.g. the link in a chat message, the password read aloud on a call), so that intercepting one alone isn't sufficient to get in.
6. As a recipient with no Tailscale, no VPN, and no special setup, I want to open a plain HTTPS link, enter a password once, and use the real app through its real login screen, so that the demo feels like using the actual product, not a workaround.
7. As a developer, I want my recipient to sign in with one of the already-seeded test accounts, so that I don't need to provision a separate account just for this share, given the underlying data is synthetic regardless of who signs in.
8. As a developer, I want `make tunnel-up` / `make tunnel-down` to own the ngrok processes' lifecycle independently of the frontend/auth dev servers, so that starting or stopping public access doesn't interfere with `db-up`, `auth-run`, or plain `frontend-run` for anyone not using it.
9. As a developer not using this feature, I want zero change to `make frontend-run`, `make auth-run`, `make backend-run`, or any other existing target's behavior, so that this stays entirely additive, opt-in tooling.
10. As a maintainer, I want a clear, discoverable reason this repo uses ngrok here specifically, given ADR-0009 chose Tailscale specifically to avoid public exposure for a different use case (personal phone access), so that a future reader doesn't conclude one of the two ADRs is simply wrong or that the reversal was accidental.
11. As a maintainer, I want it documented that Basic Auth can only gate the frontend tunnel and not `cognito-local`'s tunnel (Amplify's client-side calls to it carry no Basic Auth credentials, so gating it too would break every sign-in), so that this known, accepted gap doesn't get "discovered" and treated as an oversight later.
12. As a maintainer, I want confirmation that this feature introduces no PHI or production-credential exposure, so that a HIPAA/HITRUST-baseline app's local-dev convenience doesn't become a compliance concern — it only ever tunnels the same non-production, placeholder-credentialed local stack ADR-0007/0008/0009 already established.
13. As a CI pipeline, I want to keep passing without ngrok, an authtoken, or any of this feature's tooling ever being present, so that this stays purely opt-in local tooling with zero effect on anything automated.
14. As a developer setting this up for the first time, I want it documented that I need my own free ngrok account and authtoken configured (`ngrok config add-authtoken ...`) before any of this works, so that I'm not confused by a cryptic failure the first time I try `make tunnel-up`.

## Implementation Decisions

- **Scope**: two ngrok tunnels, fronting exactly the same two services ADR-0009 identified as needing phone/public reachability — the frontend dev server (`:5173`) and `cognito-local` (`:9229`). The backend (`:8000`) needs no tunnel, unchanged from ADR-0009's reasoning: the frontend's `/api` proxy calls it server-side, from the same machine, never from a remote browser.
- **One unified mechanism for two audiences**: unlike the Tailscale design (which distinguished "your own devices" from Funnel's "expose one thing publicly"), a public ngrok URL is the same operation regardless of who opens it — there is no separate "phone mode" and "sharing mode" here, just one public-access feature.
- **Tool choice, reversing ADR-0009's own reasoning on purpose**: ngrok, not Tailscale Funnel, specifically because the audience changed from "the developer's own paired devices" to "an arbitrary third party who won't install anything." A new ADR records this explicitly, including that it knowingly contradicts ADR-0009's stated preference for the *other* use case.
- **Tunnel lifecycle — new `tunnel-up` / `tunnel-down` Makefile targets**: `tunnel-up` starts both ngrok tunnels (one per service, each independently configured/labeled so they can be told apart later) and waits until ngrok's local API reports them ready; `tunnel-down` stops them. This mirrors the existing `db-up`/`db-down` and `auth-run`/`auth-down` pattern of a dedicated lifecycle pair per piece of infrastructure this repo's local tooling manages.
- **Hostname resolution — auto-detected, not manually supplied**: a new shared function (see Testing Decisions) queries ngrok's local API (`http://127.0.0.1:4040/api/tunnels`, which only exists while `tunnel-up` has tunnels running) and returns the current public URL for a named tunnel. New `frontend-run-public` and `auth-run-public` Makefile targets each call this lookup for their respective tunnel, inject the result as the same environment variable the underlying command already expects, and then delegate straight to the existing `frontend-run` / `auth-run` recipe — so `vite.config.ts` and `local/cognito/seed.mjs` need only the same shape of "is an externally-reachable hostname present" conditional ADR-0009 already established, not new logic of their own. If a needed tunnel isn't up yet, the new targets fail with a clear message pointing at `make tunnel-up`, rather than silently falling back to `localhost`.
- **`vite.config.ts`'s `allowedHosts` for the ngrok case must be an exact hostname match, not a suffix wildcard.** This is a deliberate departure from ADR-0009's `.ts.net` suffix pattern: `.ts.net` is safe as a wildcard because it's a private namespace Tailscale only hands to the developer's own tailnet devices, but ngrok's free-tier domains (e.g. `*.ngrok-free.app`) are a *shared public suffix* used by any ngrok account — a suffix wildcard there would accept `Host` headers from anyone else's unrelated ngrok tunnel, not just this one. The exact current session's hostname (obtained via the same auto-detect lookup) is used instead, which is also fine operationally since it already needs to be re-resolved every session anyway.
- **Basic Auth gate on the frontend tunnel only**, with a **freshly generated password each time `tunnel-up` runs**, printed to the terminal (not written to any file the developer might accidentally commit or leave lying around). `cognito-local`'s tunnel is deliberately left without Basic Auth: Amplify's client-side calls to it carry no Basic Auth credentials, so gating it too would 401 every sign-in attempt, and there is no code change to the auth client in scope for this feature to fix that. The accepted residual exposure is narrow — it only matters against someone who obtains that second tunnel's URL directly, not through the (gated) shared link — and is documented as a known, deliberate gap, not a discovered flaw.
- **Credentials for the shared recipient**: the existing seeded test accounts (`local-admin`, `local-clinic-ops`, `local-new-hire` — `local/cognito/README.md`). No separate account is provisioned for this feature.
- **Prerequisite, not automated**: a free ngrok account and a configured authtoken (`ngrok config add-authtoken <token>`) on the developer's machine — a manual, one-time step outside this feature's scope, in the same category as ADR-0009's Tailscale account sign-in.
- **No changes to `backend`, Postgres, or `docker-compose.yml`** — identical reasoning to ADR-0009.
- **PR #2 / `feature/phone-access-tailscale` is closed and its branch deleted** rather than repurposed — this feature gets its own clean branch, spec, ticket, and ADR, since nothing from the Tailscale attempt ever merged to `main`.
- **Documentation**: a new `docs/adr/0009-public-access-via-ngrok.md` (the number is reused — ADR-0009 for Tailscale never merged, so there's no collision) records the ngrok-vs-Tailscale-Funnel reasoning, the exact-match-vs-suffix-wildcard distinction, the Basic-Auth-can't-cover-both-tunnels gap, and the auto-detect-vs-manual reversal relative to ADR-0009's explicit-hostname choice (and why ngrok's every-session-rotating hostname makes that reversal correct rather than inconsistent). `README.md` and/or `local/cognito/README.md` gain a section documenting the new `make tunnel-up`/`tunnel-down`/`frontend-run-public`/`auth-run-public` targets and the one-time ngrok account setup step.

## Testing Decisions

- **What makes a good test here**: unlike ADR-0008 (docker-compose) and ADR-0009 (Tailscale), this feature contains one piece of genuine branching logic worth isolating — finding a specific tunnel's public URL inside ngrok's local API response, given that the API can report zero tunnels, the wrong tunnels, or the right tunnel not yet fully established. This is exactly the shape of seam ADR-0007's `resolveLocalAuthOverride()` set the precedent for: a pure function, no network I/O inside the function itself, fed fixture data.
- **Modules tested**: a new shared function (name to be decided at implementation time, e.g. `findTunnelUrl(tunnelsResponse, name)`) living in a new `local/ngrok/` directory (mirroring `local/cognito/`'s existing role as this repo's home for local-only, non-production tooling). It takes an already-fetched ngrok API JSON payload and a tunnel name, and returns that tunnel's current public URL, or a clear "not found" result — the actual HTTP fetch against `localhost:4040` is a separate, thin, untested wrapper around this pure function, following the same "isolate the branching, don't test the I/O" split ADR-0007's spec used for `resolveLocalAuthOverride()` versus the untested live sign-in round-trip.
- **Test cases**: the named tunnel present and up (returns its URL), the named tunnel absent from the response (ngrok running but that specific tunnel not configured), and an empty/malformed tunnels list (ngrok not fully started yet) — mirroring the kind of fixture-driven unit test already established for `frontend/src/auth/cognito.test.ts`.
- **Prior art**: `frontend/src/auth/cognito.test.ts` (ADR-0007) for the "isolate the one pure decision point, unit test it" pattern; `frontend/src/auth/tokenStore.test.ts` and `frontend/src/api/client.test.ts` for this repo's general plain-Vitest, no-DOM-mocking test style. `local/ngrok/` will need its own minimal test setup (a `package.json` with a test script, mirroring `local/cognito/package.json`'s existing role), since `local/cognito/` currently has none — this is new, not reused, infrastructure, but scoped to exactly the one function that needs it.
- **Explicitly not automated-tested, and why**: the two Makefile targets' actual orchestration (`tunnel-up` starting real ngrok processes, `frontend-run-public`/`auth-run-public` calling the real local API and launching real dev servers) is empirically verified at implementation time, not covered by an automated test — this mirrors ADR-0008 and ADR-0009's treatment of their own Makefile-target orchestration. The end-to-end claim this spec exists to deliver — a real third party, with no special setup, opening the link and signing in — is also an empirical, human-run check, not something CI can exercise.
- **Required empirical verification at implementation time** (acceptance checks, not automated tests):
  - Whether ngrok's free tier actually supports two simultaneous tunnels from one agent is confirmed by trying it, not assumed — if it doesn't, this may require sequencing the tunnels or revisiting scope, and that finding must be written into the ADR either way.
  - With both tunnels up, `frontend-run-public` binds Vite externally, allow-lists the exact current frontend tunnel hostname, and a request through that tunnel's actual public URL succeeds (not just a synthetic `curl` against localhost with a spoofed Host header, though that remains a useful mechanism-level check too).
  - The frontend tunnel's Basic Auth gate actually challenges an unauthenticated request and admits one carrying the printed credentials.
  - `auth-run-public` seeds `frontend/.env.local`'s `VITE_COGNITO_LOCAL_ENDPOINT` with the `cognito-local` tunnel's current public URL, and a sign-in through the app (reached via the frontend tunnel) actually succeeds end-to-end against that tunneled `cognito-local`.
  - With neither `tunnel-up` nor either `-public` target ever invoked, `make backend-lint`, `make backend-test`, `make frontend-lint`, `make frontend-test`, and `make frontend-build` all still pass unchanged.

## Out of Scope

- Personal phone access via Tailscale — that's ADR-0009's (abandoned, unmerged) territory conceptually, but this spec doesn't revisit or replace a shipped feature, since none shipped. If personal phone access is wanted later, it's a separate decision, not assumed to also be solved by this feature.
- Gating `cognito-local`'s tunnel with Basic Auth, or any change to the Amplify auth client needed to make that possible.
- Paid ngrok features (reserved/stable domains, OAuth-based access instead of Basic Auth, more than two simultaneous tunnels).
- A new one-off Cognito account for shared-link recipients — the existing seeded accounts are used as-is.
- Any change to production Cognito, production auth flow, or anything covered by ADR-0006/ADR-0007.
- Automating ngrok account creation or authtoken configuration.
- CI: no CI job exercises this feature.

## Further Notes

This spec directly follows a `/grill-with-docs` interview in which the user initially asked for ngrok while an unmerged, in-progress Tailscale-based PR (#2, ADR-0009) already existed for a *different* use case (personal phone access). The interview surfaced that tension explicitly rather than either silently complying or refusing, established that the two use cases were genuinely different (not a change of mind about the same problem), and confirmed that the Tailscale attempt should be abandoned entirely (branch deleted, PR closed) rather than repurposed in place, since nothing had actually merged. A related but explicitly out-of-scope finding from that same investigation: separately from this feature, an earlier docker-compose commit (`eb10e65`, ADR-0008) exists on the local `main` branch but was never pushed to `origin/main` — this is unrelated to public access via ngrok and is flagged here only so it isn't lost.
