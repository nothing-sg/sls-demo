# Local Cognito auth testing (via AWS Amplify + cognito-local)

## Problem Statement

Frontend developers on sls-best-practice cannot exercise the app's real sign-in flow without a deployed AWS Cognito User Pool. Since nearly every screen in the app requires an authenticated, role-checked session (see ADR-0004's RBAC model), this makes routine UI iteration slow, dependent on AWS access, and dependent on someone having already run `sam deploy` against a real AWS account — there is currently no way to click through the app locally at all without that.

## Solution

A developer runs a new `make auth-run` target, which starts a local Cognito-compatible auth server (`cognito-local`) pre-seeded with test accounts for each RBAC role (`admin`, `clinic_ops`), plus one account left in the "must set a new password" state. The developer then runs `make frontend-run` as usual and signs in through the app's actual login screen — the same UI, same code paths as production — against this local server instead of real AWS. Everything downstream of a successful sign-in (RBAC-gated navigation, the Patients/Appointments/Audit Log screens, the deactivate-patient flow) works exactly as it would against a real deployment. A developer who is deliberately testing against a real deployed Cognito pool instead is entirely unaffected — this tooling is opt-in and never auto-starts.

## User Stories

1. As a frontend developer, I want to run the app fully locally without needing a deployed AWS Cognito User Pool, so that I can iterate on UI without AWS access or cost.
2. As a frontend developer, I want to sign in through the app's actual login screen against a local auth server, so that my local testing exercises the real login UI code path, not a mocked one.
3. As a frontend developer, I want pre-seeded test accounts for each RBAC role (admin, clinic_ops), so that I can verify role-gated UI (e.g. the Deactivate button, the Audit Log nav link) without manually provisioning Cognito users.
4. As a frontend developer, I want a pre-seeded account left in the "must set a new password" state, so that I can exercise the first-sign-in / `FORCE_CHANGE_PASSWORD` screen the app already implements, without having to hand-create that state myself.
5. As a frontend developer, I want the local auth server's state to reset every time I start it, so that a broken local environment is never the cause of a bug I can't reproduce — restarting always gets me back to a known-good state.
6. As a frontend developer, I want to start the local auth server with a single command in its own terminal, so that it's obviously a separate long-running process from the frontend/backend dev servers, and I can choose not to run it when I'm deliberately testing against a real deployed Cognito pool instead.
7. As a frontend developer already running `frontend-run` against a real deployed Cognito pool, I want that workflow to keep working exactly as before, so that adding local-auth tooling doesn't regress anyone not using it.
8. As a maintainer, I want the local/production authentication divergence (different auth flow type, different endpoint) to be documented and explicit in code, so that nobody mistakes local testing for a full guarantee that production SRP auth works identically.
9. As a maintainer, I want the production Cognito configuration (SRP-only, MFA on) to remain completely unchanged by this work, so that adding local dev tooling never weakens the real security posture.
10. As a maintainer reading the code later, I want a clear, discoverable reason (an ADR) for why local auth uses a different flow than production, so that this doesn't read as an accidental inconsistency.
11. As a maintainer, I want the switch from `amazon-cognito-identity-js` to AWS Amplify's Auth module recorded as a deliberate decision with its rationale, so that a future contributor doesn't wonder why the "officially recommended" library wasn't already in use, or attempt to "fix" it back to the old one.
12. As a CI pipeline, I want the build, lint, and test steps to keep passing without cognito-local running, so that this local-only tooling never becomes a hard CI dependency.
13. As a frontend developer, I want the local Cognito User Pool/Client IDs written automatically into my local env file after seeding, so that I don't have to manually copy values out of terminal output.
14. As a frontend developer, I want clear documentation of exactly which parts of the sign-in experience local testing does and does not cover (e.g. if `FORCE_CHANGE_PASSWORD` turns out unsupported locally), so that I know when I still need to test against a real deployed pool instead.
15. As a security-conscious reviewer, I want confirmation that no PHI or production credentials are involved anywhere in this local tooling, so that this local-dev convenience doesn't introduce a compliance concern for a HIPAA-scoped app.
16. As a frontend developer, I want the local auth server's dependency footprint (cognito-local, any seed-script dependencies) kept out of the production bundle, so that local-only tooling never affects what ships to real users.
17. As a new contributor cloning the repo, I want a documented, minimal set of steps (install, run, seed) to get a working local sign-in loop, so that onboarding doesn't require deploying real AWS infrastructure first.
18. As a frontend developer, I want the app's use of AWS Amplify's Auth module to still perform the same real SRP authentication flow against production Cognito that the app used before this change, so that switching libraries doesn't change production's actual security behavior.

## Implementation Decisions

- **Client library**: switch `frontend/src/auth/` from `amazon-cognito-identity-js` to AWS Amplify's Auth module (`aws-amplify` v6, using the modular `aws-amplify/auth` import surface: `signIn`, `confirmSignIn`, `signOut`, `fetchAuthSession`). Production authentication continues to use the default SRP (`USER_SRP_AUTH`) flow via Amplify. No change to `infra/modules/api.yaml`'s `UserPoolClient` (`ALLOW_USER_SRP_AUTH` + `ALLOW_REFRESH_TOKEN_AUTH` only) — production behavior is unchanged, only the library issuing the same protocol changes.
- Amplify is configured once via `Amplify.configure(...)` with `userPoolId` and `userPoolClientId`, plus — only when local mode is active — a `userPoolEndpoint` override pointing at the local auth server.
- **Local/production divergence** is controlled by a single new frontend env var, `VITE_COGNITO_LOCAL_ENDPOINT` (unset in production and in any `.env.local` pointed at a real deployed pool). When set: `userPoolEndpoint` is passed to `Amplify.configure`, and sign-in is issued with `authFlowType: "USER_PASSWORD_AUTH"` instead of the default SRP. When unset: behavior is identical to before this feature (default SRP, real AWS endpoint).
- **New-password challenge handling**: `signIn()`'s `nextStep.signInStep === "CONFIRM_SIGN_IN_WITH_NEW_PASSWORD_REQUIRED"` replaces the old `newPasswordRequired` callback; resolved via `confirmSignIn({ challengeResponse: newPassword })`. `frontend/src/pages/LoginPage.tsx`'s two-step UI (sign-in form, then new-password form) stays structurally the same — only the underlying calls in `frontend/src/auth/cognito.ts` / `AuthContext.tsx` change.
- **Local auth server**: `cognito-local` (the npm package), added as a `frontend/` devDependency. Chosen over LocalStack, which requires a paid subscription tier for Cognito on a commercial product and has reportedly broken SRP support even on paid tiers — moot either way here, since local mode uses `USER_PASSWORD_AUTH`, which `cognito-local` does support (confirmed; it does not support `USER_SRP_AUTH` at all, which is the reason the local/prod flow diverges rather than being identical).
- **New top-level `local/cognito/` directory** holds: any `cognito-local` server config needed (issuer domain, MFA-off setting) and a Node seed script (using `@aws-sdk/client-cognito-identity-provider`, a dev-only dependency with no production bundle impact) that: creates a local User Pool with a `custom:role` schema attribute, creates a User Pool Client with `ALLOW_USER_PASSWORD_AUTH` (+ refresh token) enabled, creates the three seed users below, and writes the resulting pool/client IDs automatically into `frontend/.env.local`.
- **Seed users**: `local-admin` and `local-clinic-ops`, both created with a permanent password and the corresponding `custom:role` value, for fast day-to-day iteration. A third, `local-new-hire`, created and deliberately left in `FORCE_CHANGE_PASSWORD` status, specifically to exercise the new-password screen — *contingent on empirical confirmation that `cognito-local`'s `AdminCreateUser` actually produces that challenge state* (its own documentation marks this API as only partially implemented). If confirmed unsupported: drop this seed user and document the gap explicitly in `local/cognito/README.md` rather than simulate the challenge client-side.
- **MFA**: the local User Pool runs with MFA off. This is a deliberate, documented divergence from the real pool's `MfaConfiguration: "ON"` (`infra/modules/api.yaml`) — `cognito-local` cannot honor TOTP MFA at all, and exercising MFA enrollment isn't this feature's goal.
- **State persistence**: ephemeral by default. `cognito-local`'s on-disk state directory is cleared/reset every time the local server starts (not preserved across restarts), and is gitignored.
- **Orchestration**: a new `make auth-run` Makefile target starts `cognito-local`, waits for it to be ready, runs the seed script once, then keeps the server running in the foreground (developer-managed, own terminal — Ctrl+C stops it) — matching the existing `backend-run`/`frontend-run` pattern of separate, explicitly-started dev processes. It is never auto-started by any other `make` target.
- **Backend**: no changes. `backend/src/shared/auth.py`'s existing TODO (verify the JWT signature against Cognito's real JWKS instead of decoding unverified) is explicitly out of scope for this feature — `cognito-local` is reported to expose a working JWKS endpoint, which may make closing that TODO easier later, but implementing it is separate work.
- **Documentation**: `docs/adr/0006-*.md` records the Amplify switch (supersedes the relevant part of ADR-0005's stated rationale for `amazon-cognito-identity-js`); `docs/adr/0007-*.md` records the local-testing design (the SRP/local-vs-prod divergence, MFA-off, ephemeral state, seed-user rationale). `local/cognito/README.md` documents the concrete seeded accounts/credentials and any known local-testing gaps. `README.md`'s existing "Frontend" section gets a pointer to `make auth-run`.

## Testing Decisions

- **What makes a good test here**: pure, deterministic logic only. The one true seam in this feature is the config-selection function in `frontend/src/auth/cognito.ts` that decides `userPoolEndpoint`/`authFlowType` based on whether `VITE_COGNITO_LOCAL_ENDPOINT` is set — a plain function with no I/O, testable exactly like the existing `unwrap()` and token-store tests.
- **Modules tested**: `frontend/src/auth/cognito.ts`'s config-selection logic (new unit test file, following the existing `*.test.ts` convention).
- **Explicitly not automated-tested, and why**: the actual sign-in round-trip against `cognito-local` (a live local network service — verified by a human running `make auth-run` and clicking through the app, not CI); the seed script and `cognito-local` orchestration itself (correctness here means "did it produce a working local environment," which is a one-time empirical check at implementation time, not an ongoing automated test); anything about the real, deployed Cognito flow (already an unverifiable-without-a-deployment limitation of this project, unchanged by this feature). No CI-wired end-to-end sign-in test is part of this feature (see Out of Scope).
- **Prior art in this codebase**: `frontend/src/api/client.test.ts` and `frontend/src/auth/tokenStore.test.ts` — both plain Vitest, `node` environment, no DOM/network mocking, testing pure logic extracted from an otherwise I/O-heavy module. The new test for the config-selection function follows this exact pattern.
- **Required non-test verification at implementation time** (acceptance checks, not automated tests): empirically confirm whether `cognito-local`'s `AdminCreateUser` actually produces a `FORCE_CHANGE_PASSWORD` state (determines whether `local-new-hire` ships or the gap gets documented instead, per the Implementation Decisions above); confirm the app still builds/lints/typechecks cleanly with the Amplify swap; confirm production bundle size doesn't regress (verify Amplify's tree-shaking claim against this project's actual Vite build output rather than trusting vendor documentation, consistent with how this project caught the TanStack Table version mismatch and the "global is not defined" bug via live verification rather than assumption).

## Out of Scope

- Local Postgres orchestration (a separate, pre-existing gap in local dev setup — the backend already has no automated local database, unrelated to auth).
- Implementing backend JWT signature verification against Cognito's real JWKS (`backend/src/shared/auth.py`'s existing TODO). This feature does not close that TODO, though `cognito-local`'s JWKS support may make doing so easier later.
- Automated end-to-end (e.g. Playwright) sign-in tests wired into CI. This feature only makes that possible; actually adding it is a separate, deliberate decision.
- Any change to the real, deployed Cognito User Pool's configuration (`infra/modules/api.yaml`) — MFA stays on, SRP-only stays the only allowed flow, in production.
- Self-service user signup or role-assignment UI. Accounts remain admin-provisioned only, both locally and in production (per ADR-0004) — the local seed script is not a general-purpose "create a Cognito user" tool, just a fixture for this feature's three test accounts.

## Further Notes

- This spec's design came out of a `/grill-with-docs` session that included two rounds of live fact-finding research which materially changed the design, not just confirmed assumptions: (1) both `cognito-local` and LocalStack were confirmed unable to emulate the SRP flow the app originally used — LocalStack additionally requires a paid tier for Cognito on a commercial product — which is the actual reason a local/production auth-flow divergence exists at all, rather than a clean 1:1 local mirror; (2) the switch to AWS Amplify was verified against current AWS/Amplify documentation (not assumed) to confirm it's a genuine current recommendation, that it exposes the `userPoolEndpoint` override this whole design depends on, and that it does not regress bundle size.
- At the time this spec was written, no implementation code has been merged for this feature. `local-admin`, `local-clinic-ops`, `local-new-hire` are placeholder usernames chosen for clarity during design; whoever implements this may adjust naming as long as it stays documented in `local/cognito/README.md`.
- The single testing seam (see Testing Decisions) was explicitly proposed to and confirmed by the user before this spec was finalized.
