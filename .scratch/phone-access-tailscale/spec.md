# Phone access to local dev via Tailscale

## Problem Statement

A developer running the local dev stack (`make backend-run`, `make frontend-run`, plus the Docker-based Postgres/cognito-local setup from `docs/adr/0008-local-dev-docker-compose.md`) cannot open the app on their phone to check how it looks or behaves on a real mobile device, because both dev servers are bound to `localhost` only. This gets harder, not easier, when the developer is on a public network (a coffee shop, an airport, a hotel) rather than home WiFi: most public networks enable client/AP isolation that blocks device-to-device traffic even when phone and laptop show the "same" network name, so simply binding to `0.0.0.0` and finding a LAN IP is unreliable there. Separately, the app requires an authenticated, role-checked session for nearly every screen (ADR-0004's RBAC model), so phone access that can't also complete local sign-in isn't useful for anything beyond the login page itself.

## Solution

A developer installs Tailscale (a private mesh VPN) on their phone and Mac once, giving the Mac a stable private hostname reachable from the phone regardless of which physical network either device is actually on — no public URL, no exposure beyond the developer's own two devices. Setting one shared environment variable, `PHONE_HOST=<tailscale-hostname>`, before running the existing `make frontend-run` and `make auth-run` targets switches both into phone-accessible mode: Vite binds externally and allow-lists the Tailscale hostname pattern, and the seeded local Cognito endpoint written to `frontend/.env.local` points at the same hostname instead of `localhost`. Leaving `PHONE_HOST` unset leaves both targets' behavior completely unchanged from today.

## User Stories

1. As a developer, I want to open the app's login screen on my phone's browser, so that I can check how it actually renders on a real mobile viewport instead of guessing from a resized desktop window.
2. As a developer, I want to complete a real local sign-in on my phone (not just view the unauthenticated login page), so that I can check role-gated UI (the Deactivate button, the Audit Log nav link) on a real device, not just on desktop.
3. As a developer on a public network (coffee shop, airport, hotel), I want phone access to work even when my phone and laptop aren't on the same LAN segment or the network blocks device-to-device traffic, so that "public network" doesn't mean "phone testing is off the table today."
4. As a developer, I want phone access to require an explicit action to turn on, so that my dev server never becomes reachable beyond `localhost` by accident during normal (non-phone) development.
5. As a developer, I want turning phone access on or off to be a single environment variable, so that I don't have to remember and coordinate multiple separate flags across the frontend and the local auth server.
6. As a developer, I want `frontend/.env.local`'s Cognito endpoint value to keep being written automatically by the existing seed script, so that enabling phone mode doesn't require me to hand-edit a file whose whole documented contract (`local/cognito/README.md`) is that it's generated, not hand-maintained.
7. As a developer, I want the backend to require no changes at all for this feature, so that the scope stays proportional to "let me view the frontend on my phone," not "expose my whole local stack to the internet."
8. As a developer who renames their Mac or Tailscale device later, I want the Vite configuration to keep working without an edit, so that a routine device rename doesn't quietly break phone-testing until I notice and remember why.
9. As a maintainer, I want a clear, discoverable reason (an ADR) for why Tailscale was chosen over a public tunnel like ngrok, and why the hostname is supplied explicitly rather than auto-detected, so that these don't read as arbitrary choices to someone extending this later.
10. As a maintainer, I want confirmation that this feature introduces no PHI or production-credential exposure risk, so that a HIPAA/HITRUST-baseline app's local-dev convenience doesn't become a compliance concern (this feature only ever touches the same non-production, placeholder-credentialed local stack that ADR-0007/0008 already established).
11. As a CI pipeline, I want to keep passing without Tailscale, a phone, or any of this feature's env vars ever being present, so that this stays purely opt-in local tooling with zero effect on anything automated.
12. As a developer who doesn't want or need phone access, I want zero change to my existing `make frontend-run` / `make auth-run` workflow, so that this feature is invisible unless I specifically opt into it.

## Implementation Decisions

- **Scope**: only the frontend dev server (Vite, `:5173`) and the local Cognito auth server (`cognito-local`, `:9229`) need to become phone-reachable. The backend (`uvicorn`, `:8000`) needs no change — the frontend's existing `/api` proxy calls it from the Vite process itself (server-side, same machine), so it's never reached directly by the phone's browser.
- **Mechanism**: Tailscale, not a public tunnel (e.g. ngrok). This is a personal, two-device use case, and this repo is a HIPAA/HITRUST-baseline product where local-dev tooling should default to the least exposure that solves the problem — a private mesh between the developer's own devices, rather than a URL anyone with the link could reach. Tailscale also gives the whole machine one stable hostname across ports, avoiding the need to separately tunnel `:5173` and `:9229` the way a per-port tunnel tool would require. Installing and signing into Tailscale on both devices is a manual, one-time setup step for the developer — outside this feature's automatable scope.
- **Single opt-in switch**: one environment variable, `PHONE_HOST`, set to the developer's Tailscale hostname, gates both changes below. Unset (the default): both targets behave exactly as they do today. This was chosen over auto-detecting the hostname via the `tailscale` CLI, to avoid a hard runtime dependency on that CLI being installed, on `PATH`, and already logged in at the moment `make` runs, for a value that's cheap to look up once (`tailscale status`) and reuse.
- **Frontend (`frontend/vite.config.ts`)**: when `PHONE_HOST` is set, the dev server binds externally (`host: true` / `0.0.0.0`) and `server.allowedHosts` gains an entry matching the `.ts.net` suffix — needed because the installed Vite version (5.4.21) otherwise rejects any request whose `Host` header isn't localhost, an IP literal, or explicitly allowed, returning a 403 ("Blocked request..."). A suffix match (rather than pinning the exact current hostname) was chosen so a later machine or tailnet rename doesn't silently break this. When `PHONE_HOST` is unset, `vite.config.ts` produces byte-for-byte the same config as before this feature.
- **Local auth server seeding (`local/cognito/seed.mjs`)**: when `PHONE_HOST` is set, the value written to `frontend/.env.local`'s `VITE_COGNITO_LOCAL_ENDPOINT` key uses that hostname (`http://<PHONE_HOST>:9229`) instead of the hardcoded `http://localhost:9229` — necessary because Amplify's client-side auth calls hit this endpoint directly from the phone's own browser (unlike `/api`, which is proxied server-side), and "localhost" from the phone's perspective resolves to the phone itself, not the developer's Mac. All other seeding behavior (accounts created, `local/cognito/README.md`'s documented account table, the "only these three keys are touched" contract) is unchanged.
- **`cognito-local` container / `docker-compose.yml`**: no changes anticipated. `docs/adr/0008-local-dev-docker-compose.md`'s `HOST=0.0.0.0` fix already binds the container's server broadly, and the published Docker port was already confirmed (during that ADR's implementation) to listen on all host interfaces, not just loopback — this should already be reachable via a Tailscale-assigned interface without further changes, but must be confirmed empirically at implementation time rather than assumed.
- **Backend**: no changes.
- **Existing Makefile targets, not a new one**: `make frontend-run` and `make auth-run` are extended to read `PHONE_HOST` when present, rather than introducing a new combined entry point (e.g. `make phone-run`). This preserves the existing pattern of independently-runnable targets — a phone-testing session still benefits from being able to start just one or the other, exactly as today.
- **Documentation**: `docs/adr/0009-phone-access-via-tailscale.md` records why Tailscale was chosen over a public tunnel, why the host-allowlist is a suffix wildcard rather than a pinned hostname, and why the hostname is supplied explicitly rather than auto-detected. `README.md` and/or `local/cognito/README.md` gain a short section documenting `PHONE_HOST` and the one-time Tailscale setup step.

## Testing Decisions

- **What makes a good test here**: this feature's logic is two independent, one-line, env-var-gated conditionals (Vite's `host`/`allowedHosts`, and the endpoint string `seed.mjs` writes) living in two separate toolchains (`frontend/`'s Vite config and `local/cognito/`'s Node script) with no shared runtime between them. Neither branch has the decision complexity that made ADR-0007's `resolveLocalAuthOverride()` (choosing between two full auth configs and flow types) worth isolating into a tested pure function — this is materially simpler, matching the class of change ADR-0008's spec already treated as having "no unit-testable seam."
- **Modules tested**: none. No new `*.test.ts` coverage is introduced. Existing `vitest` (frontend) and `pytest` (backend) suites are unaffected and must keep passing with `PHONE_HOST` unset and Tailscale entirely absent from the environment.
- **Required empirical verification at implementation time** (acceptance checks, not automated tests, following the same pattern used for ADR-0007's original cognito-local orchestration and ADR-0008's compose setup):
  - With `PHONE_HOST` unset, `make frontend-run` and `make auth-run` behave identically to before this feature (dev server localhost-only, seeded endpoint is `http://localhost:9229`) — confirmed by diffing behavior, not assumed from the code alone.
  - With `PHONE_HOST` set to a real Tailscale hostname, a request to the Vite dev server carrying that Host header succeeds rather than being 403'd, confirming the `allowedHosts` entry actually matches.
  - `local/cognito/seed.mjs` run with `PHONE_HOST` set writes `http://<PHONE_HOST>:9229` into `frontend/.env.local`'s `VITE_COGNITO_LOCAL_ENDPOINT`, and the other two keys (`VITE_COGNITO_USER_POOL_ID`, `VITE_COGNITO_CLIENT_ID`) are unaffected.
  - The `cognito-local` container is confirmed reachable via the Mac's actual Tailscale-assigned interface (not just `localhost` or a Docker-internal check) — this is the specific claim in Implementation Decisions flagged as "must be confirmed, not assumed."
  - End-to-end: from a real phone with Tailscale installed and connected to the same tailnet, opening `http://<PHONE_HOST>:5173`, completing a real sign-in with a seeded account (`local-admin`/`LocalAdmin123!`), and confirming role-gated UI renders correctly — the actual user-facing behavior this spec exists to deliver, not just its component pieces in isolation.
  - `make backend-lint`, `make backend-test`, `make frontend-lint`, `make frontend-test`, and `make frontend-build` all still pass unchanged.

## Out of Scope

- Auto-detecting the Tailscale hostname via the `tailscale` CLI — the hostname is supplied explicitly via `PHONE_HOST`.
- A new combined `make phone-run` (or similarly named) Makefile target — this extends the two existing targets instead.
- Any change to the backend (`uvicorn`), Postgres, or `docker-compose.yml`'s service definitions — only `vite.config.ts` and `seed.mjs` change.
- Supporting ngrok or any other public-tunnel tool as an alternative to Tailscale.
- Installing or configuring Tailscale itself on the developer's phone or Mac, or the account sign-in it requires — a manual, one-time step outside this feature's scope.
- Any change to production Cognito, production auth flow, or anything covered by ADR-0006/ADR-0007 — this feature only affects the already-local, already-non-production `cognito-local` path.
- CI: no CI job exercises this feature; it must keep passing with none of `PHONE_HOST`/Tailscale present, exactly as today.

## Further Notes

This spec was written after design-but-before-implementation (via `/to-spec`), synthesizing a `/grill-with-docs` interview earlier in the same session, immediately following the same pattern used for `docs/adr/0008-local-dev-docker-compose.md` and `.scratch/local-dev-docker-compose/spec.md`. Two facts from that interview are worth restating here because they're easy to get wrong by assumption rather than by checking: (1) Vite 5.4.21's `allowedHosts` rejection is real and confirmed by reading the installed package's own source, not inferred from general Vite documentation that might describe a different major version's behavior; (2) the backend needs zero changes specifically because the `/api` proxy is a server-side call Vite's own process makes to `localhost:8000`, not something the phone's browser ever touches directly — it would be an easy, incorrect assumption to think the backend also needs a Tailscale-facing bind.
