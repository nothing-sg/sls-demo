# ADR-0005: Frontend stack — shadcn/ui, TanStack Query + Table, React Router, direct Cognito auth

## Status

Accepted — 2026-09-04

## Context

The backend (ADR-0001–0004) exposes a REST API behind Cognito auth with two RBAC roles. The frontend needed: a component library, a way to render the Patients/Appointments/Audit Log tables, client-side routing across a few pages, server-state management against the API, and some way to actually get a Cognito token to call it with.

## Decisions

**Component library: shadcn/ui, scaffolded via its CLI (`npx shadcn@latest init`), not hand-written.** shadcn isn't an npm package — it copies component source into `frontend/src/components/ui/`, so it's ours to edit, and upgrades are opt-in (`shadcn add --overwrite`) rather than forced by a version bump. The CLI's current default generates against **Base UI** (`@base-ui/react`), not Radix — that's simply what `shadcn@latest` ships today with no `--base` override; the generated components (`Dialog`, `Select`, `DropdownMenu`, etc.) use Base UI's `render={<Element />}` composition prop in place of Radix's `asChild`.

**React 19, not 18.** The generated `ui/*.tsx` components (`Button`, `Input`, etc.) are plain function components, not wrapped in `React.forwardRef`. That only works because React 19 supports `ref` as an ordinary prop on function components; on React 18 those refs would silently fail to attach (a console warning, and react-hook-form's uncontrolled registration degraded). Upgraded the whole frontend to React 19 rather than patch every generated file to add `forwardRef` — patching generated files defeats the point of using the CLI to keep them updatable.

**TanStack Table v8, not the `latest` tag (which resolves to v9).** `npm install @tanstack/react-table` pulled v9.2.4, a pre-release with a substantially different API (`createCoreRowModel`, `ReactTable` vs the `useReactTable`/`getCoreRowModel`/`flexRender` shape almost every current TanStack Table + shadcn guide — including shadcn's own official data-table recipe — is written against). Pinned to `^8.21.3`. One `DataTable<TData, TValue>` component (`src/components/data-table.tsx`) wraps it, reused by the Patients, Appointments, and Audit Log tables.

**TanStack Query for server state**, not hand-rolled `useEffect` fetching — cache invalidation on mutation (`useDeactivatePatient` invalidates the patients list; `useScheduleAppointment` invalidates that patient's appointments) is the pattern the rest of this stack expects.

**A typed API client generated from the backend's own OpenAPI schema** (`openapi-fetch` + `openapi-typescript`, fulfilling the plan in ADR-0003) instead of hand-written `fetch` calls or hand-written response types. `frontend/src/api/schema.d.ts` is generated by `make gen-api` and **committed** (not gitignored) — CI regenerates it from the backend's live schema and fails the build on drift, so a backend endpoint/schema change that isn't reflected in the frontend types breaks CI immediately instead of surfacing as a runtime mismatch.

**react-router-dom**, not a state-based view switch — patient detail pages need to be a real, bookmarkable/deep-linkable URL (`/patients/:patientId`), and back/forward should work.

**Direct Cognito SRP auth via `amazon-cognito-identity-js`**, not `aws-amplify`. The backend's Cognito setup (`infra/modules/api.yaml`) is already minimal — one User Pool, `ALLOW_USER_SRP_AUTH` — and Amplify's `Auth` module pulls in a much larger, more opinionated surface (analytics, storage, API layers we don't use) for the same SRP flow this lighter library implements directly. Staff accounts are admin-provisioned (`AdminCreateUser`, `FORCE_CHANGE_PASSWORD`), so the login flow has to handle Cognito's `newPasswordRequired` challenge — there's no self-service signup screen, deliberately (see ADR-0004: a self-service role field would let anyone grant themselves `admin`).

## A bug this stack combination produced, and how it surfaced

Two issues only showed up when the app was actually loaded in a browser, not from `tsc`/`eslint`/`vite build` alone:

1. **`global is not defined`** — a hard crash on first paint. `amazon-cognito-identity-js`'s crypto dependencies (`jsbn`/`asn1.js`) reference the Node.js `global` object at module-load time; Vite, unlike webpack, doesn't polyfill Node globals. Fixed with `define: { global: "globalThis" }` in `vite.config.ts`.
2. **A second crash, after the first was fixed**, from `AuthProvider`'s effect: `cognito.getCurrentSession()` threw *synchronously* (not as a promise rejection) when `VITE_COGNITO_USER_POOL_ID`/`VITE_COGNITO_CLIENT_ID` aren't set, and nothing caught it. Fixed at the source (`getCurrentSession` is now declared `async`, so any synchronous throw becomes a rejection) and defensively in `AuthContext` (a `.catch()` that falls back to signed-out rather than crashing) — a misconfigured Cognito setup now surfaces as a clear, actionable message on the sign-in form instead of a blank page.

Both were caught by actually driving the app with Playwright against the dev server, not by the type checker — worth remembering next time this stack (or `amazon-cognito-identity-js` specifically) shows up in a Vite project.

## Consequences

- Upgrading shadcn components later (`shadcn add <component> --overwrite`) may reintroduce the same forwardRef assumption — fine, since we're staying on React 19.
- The generated `ui/*.tsx` files are ours now; don't hand-edit them beyond what's necessary (className tweaks, prop additions) or the next `shadcn add --overwrite` silently clobbers the edit.
- No JWKS signature verification yet on the backend (`shared/auth.py` TODO) — same caveat ADR-0004 already states. The frontend's token handling is otherwise real: SRP auth, session refresh via the stored refresh token, ID token role claim read directly from Cognito, not mocked.
- Nobody has deployed a User Pool against this infra yet, so the sign-in flow itself (not just its failure mode) is unverified end-to-end — same class of gap as the rest of `infra/` being lint-verified but not deploy-verified.
