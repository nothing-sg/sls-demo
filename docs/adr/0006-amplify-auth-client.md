# ADR-0006: Switch frontend Cognito client from amazon-cognito-identity-js to AWS Amplify

## Status

Accepted — 2026-09-04

## Context

ADR-0005 chose `amazon-cognito-identity-js` over `aws-amplify`'s `Auth` module specifically because Amplify's `Auth` module pulled in "a much larger, more opinionated surface (analytics, storage, API layers we don't use) for the same SRP flow this lighter library implements directly." That was a fair read of the Amplify major version available at the time — pre-v6 Amplify had the "import everything" reputation the decision was reacting to.

Two things prompted revisiting it, both confirmed against current sources rather than assumed:

1. AWS's own current documentation, and `amazon-cognito-identity-js`'s own npm page, now explicitly recommend migrating off it to Amplify's Auth features ("a modern, fully-typed, and performant experience for Auth use cases with tree-shaking built-in" — the underlying rationale, per `aws-amplify/amplify-js#7627`, is SDK consolidation, not a security concern with the old library).
2. Amplify v6's modular import surface (`aws-amplify/auth`) is a genuinely different shape than the pre-v6 `Auth` singleton ADR-0005 was reacting to. AWS's own quantified figures put the Auth-only bundle at 32KB gzip in v6, down from 55KB in v5 — a real, cited tree-shaking improvement, not marketing copy.

This decision is also a prerequisite for the local-Cognito-testing feature this ADR's parent work is part of (`.scratch/local-cognito-auth/spec.md`): that feature depends on a documented, first-class Amplify v6 config field (`userPoolEndpoint`) to point sign-in at a local `cognito-local` server for development, something `amazon-cognito-identity-js` has no equivalent for. Wiring that up is separate work (ADR-0007); this ADR covers only the client-library swap itself, with production behavior unchanged.

## Decision

Replace `amazon-cognito-identity-js` with `aws-amplify` v6's modular `aws-amplify/auth` import surface (`Amplify`, `signIn`, `confirmSignIn`, `signOut`, `fetchAuthSession`) in `frontend/src/auth/`.

- Amplify is configured once — `Amplify.configure({ Auth: { Cognito: { userPoolId, userPoolClientId } } })` — from the same `VITE_COGNITO_USER_POOL_ID` / `VITE_COGNITO_CLIENT_ID` env vars as before (names unchanged).
- Production authentication is unchanged: the default `USER_SRP_AUTH` flow, against the real Cognito endpoint. `infra/modules/api.yaml`'s `UserPoolClient` config (`ALLOW_USER_SRP_AUTH` + `ALLOW_REFRESH_TOKEN_AUTH` only) is untouched — only the client library issuing the same protocol changed.
- Cognito's `NEW_PASSWORD_REQUIRED` challenge (hit on every admin-provisioned account's first sign-in, per ADR-0004) moves from `amazon-cognito-identity-js`'s `newPasswordRequired` callback — which handed back a `CognitoUser` object the caller had to hold onto and resume the challenge on — to Amplify's shape: `signIn()` returns `nextStep.signInStep === "CONFIRM_SIGN_IN_WITH_NEW_PASSWORD_REQUIRED"`, resolved via `confirmSignIn({ challengeResponse: newPassword })`. Amplify tracks the pending challenge internally, so there's no user handle to thread back through the caller. `frontend/src/pages/LoginPage.tsx`'s two-step UI (sign-in form, then new-password form) is unchanged — only the calls underneath it changed.
- Session restore uses `fetchAuthSession()`; `custom:role` is still read from the ID token's decoded payload (`session.tokens.idToken.payload`), same as before.
- This supersedes ADR-0005's client-library rationale specifically — the "much larger, more opinionated surface" concern doesn't hold the same way against Amplify v6's modular imports. It does not fully vanish, though — see Consequences.

## Consequences

- **Bundle size did not improve, and in fact regressed slightly — measured directly against this app's actual build, not assumed from vendor figures.** Before (`amazon-cognito-identity-js`): ~571 kB / ~183 kB gzip main chunk. After (`aws-amplify` v6, `aws-amplify/auth` modular imports): 607.80 kB / 191.45 kB gzip (`npm run build` in `frontend/`, read directly from its output). That's roughly +37 kB raw / +8 kB gzip (~+4.6% gzip on the main chunk). Traced into the actual built bundle: Amplify's own `Amplify.configure()` (from the `aws-amplify` package — the officially documented entry point) calls a single `parseAmplifyConfig()` function in `@aws-amplify/core` that handles every possible Amplify resource type (API/GraphQL, Geo, Predictions, Analytics, DataStore) in one function body, regardless of which service is actually configured — confirmed by grepping the built `dist/assets/index-*.js` for those service names post-build. That function isn't per-service tree-shakeable the way `aws-amplify/auth`'s `signIn`/`confirmSignIn`/etc. are. AWS's cited 32KB (v6) / 55KB (v5) figures describe the Auth module measured in isolation; they don't describe what a real app doing `Amplify.configure()` + `aws-amplify/auth` actually ships. `vite.config.ts`'s `chunkSizeWarningLimit` was bumped from 600 to 650 to reflect this (see its comment there).
  - This is exactly the kind of vendor tree-shaking claim this project's practice is to verify live rather than trust — see ADR-0005's own "bug this stack combination produced" section for the prior precedent (TanStack Table's version mismatch, the `global is not defined` crash). Worth remembering next time a library's bundle-size claim is load-bearing for a decision.
  - Not attempted: bypassing the `aws-amplify` package's `Amplify.configure()` for the lower-level `@aws-amplify/core` API directly, to dodge `parseAmplifyConfig()`. That's an undocumented, unsupported usage pattern — `cognitoUserPoolsTokenProvider` wiring is normally handled for you by the `aws-amplify` package's `configure()` — not worth the fragility for a ~4.6% gzip difference on an internal tool.
- Amplify's Auth functions have no React peer dependency (`npm info aws-amplify peerDependencies` returns empty) — no React-19-compatibility question, consistent with ADR-0005's React 19 upgrade.
- **Not independently verified end-to-end against a real deployed Cognito User Pool** — no AWS account is available in this environment, the same already-disclosed limitation ADR-0005's Consequences section states ("Nobody has deployed a User Pool against this infra yet"). Verification for this change was: code review against Amplify v6's actual shipped `.d.ts` type definitions (not docs) for every API shape used here (`SignInInput`, `ConfirmSignInInput`, `AuthSession`, the `CONFIRM_SIGN_IN_WITH_NEW_PASSWORD_REQUIRED` literal, `CognitoUserPoolConfig`'s `userPoolEndpoint` field); `npm run build` / `npm run lint` / `npm run test` all passing; and the existing unit-tested behavior (`frontend/src/auth/tokenStore.test.ts`, `frontend/src/api/client.test.ts`) continuing to pass unmodified. A live sign-in check — against `cognito-local`, not real AWS — is separate work (ADR-0007), once a local server exists to check it against.
- `amazon-cognito-identity-js`'s `global`-referencing crypto dependencies (ADR-0005's "bug this stack combination produced") are gone from the dependency tree; `vite.config.ts`'s `define: { global: "globalThis" }` is kept anyway since Amplify's own code still guards with `typeof global` in a few places, and the polyfill is zero-cost.
- The unused `buildRoleAttribute()` helper (exported from the old `cognito.ts`, "for a future admin create user flow — not wired to any UI yet") was dropped rather than ported: it doesn't map onto Amplify's client-side Auth module (admin-side user creation is an `@aws-sdk/client-cognito-identity-provider` server-side operation, not something the client Auth SDK does), and it had no callers.
